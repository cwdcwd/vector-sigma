## What this is

Completes the two open review findings from PR #61 by making the publisher
pipeline actually publish the bytes it scanned — and prove it.

Bead: `fleet-ops-r3v` (related to `fleet-ops-1py.14`, the merged PR #61, and
`fleet-ops-1py.7`, the broader prebuilt-deployment restructure).

## The defect being closed

**Finding #4 (the serious one).** `promote` ran a *second*
`docker buildx build --push` on a fresh runner and never consumed the OCI tar
or local index that `stage-and-scan` had already built and scanned. A changed
base tag, dependency drift, or any build nondeterminism could therefore put
**different, completely unscanned bytes** into GHCR, with zero cryptographic
link between what the gate scanned and what shipped. The interim safe fallback
removed the rebuild but left `promote` a no-op with the entire downstream chain
(`promote-manifest`, `verify-remote`, `scan`, `smoke`, `render`, `deploy`) at
`if: false` — safe, but it delivered nothing.

**Finding #5.** Remote verification printed a "recorded" and a "remote" digest
side by side and never compared them.

## The fix

New `registrar/src/registry/` — deliberately **outside** `registrar/src/oci-gate/`,
because `oci-gate` carries a load-bearing static and behavioural *no-network*
assertion that is what makes "the scan is local-only" provable. The only
real-network module is `fetch-transport.ts`; everything above it is exercised
against an in-memory fake and, in `registry-real-transport.test.ts`, a real
`node:http` socket.

- `oci-distribution.ts` — minimal OCI Distribution v2 client. Lower-cased
  header keys; the token lives only in an `Authorization` header; upload
  `Location` is resolved against the registry origin (scheme-aware).
- `promote.ts` — **STAGING then TAGGING.** Every blob, every per-arch manifest
  and the index are PUT *by digest* and read back and compared; **no tag is
  applied until every staged byte has been verified**. A staging failure leaves
  the registry with *zero* tags; a tagging failure stops before the index tag.
- `verify-remote.ts` — recomputes SHA-256 over the served bytes. It trusts
  neither the registry's `Docker-Content-Digest` nor the promoter's own
  promote-time return value.
- `auth.ts`, `fetch-transport.ts` — token exchange, anonymous pulls supported,
  the password used only to build one Basic header.
- `scripts/ghcr-promote-run.mjs` — the CI entry point (`promote` | `verify`).

### Workflow wiring (all three publishers)

- `stage-and-scan` now uploads the **layout tar**, not just its descriptor —
  the tar is the bytes `promote` publishes. That upload is the cryptographic
  link between scan and publish.
- `promote` downloads those tars and pushes them through the in-repo client.
  No `docker/build-push-action`, no `push: true`, no `docker/login-action`.
- `promote-manifest` is **gone**: it was a second, independent
  `docker buildx imagetools create` index-assembly path that could in
  principle produce an index differing from the locally validated one. The
  promoter now assembles the index itself, from only the scanned-and-passed
  child descriptors. One assembly path, one source of truth.
- `verify-remote` runs credential-free (no `packages:write`) and fail-closed
  through the in-repo verifier.
- `scan` / `smoke` / `render` / `deploy` are switched back **on**.

## Verification

Local gate: `npm ci && npm run build && npm test` → **743 registrar + 43
registrant tests green**, plus `bash -n deploy/e2e.sh`. (The compose E2E is
CI-only; this host has no docker.)

New suites:

- `registry-promote` — byte identity and fail-stop ordering, against a fake
  registry that records request **order**, so "no tag exists before every byte
  was verified" is asserted, not assumed.
- `registry-real-transport` — a real `node:http` registry and the real fetch
  transport: header casing as the wire sees it, `Content-Length` framing,
  `Location` session resolution, non-2xx handling. This caught a real bug
  during development (the client resolved the upload `Location` against
  `https://` unconditionally).
- `ghcr-promote-run.integration` — the **real CI script** as a child process
  over a real socket: argv parsing, the record file the verify job consumes,
  the exit code on failure, and that the credential it is handed never appears
  in its output.
- `promote-structural-gate` — rewritten from the interim `if: false` shape to
  the real-promotion contract.
- Adds `docs/ghcr-promotion-runbook.md`.

## What is NOT proven — read this before merging with intent to release

**No live GHCR write has been performed.** This lane proves the client, the
ordering, the wire behaviour and the CI contract against unit fakes, a real
local HTTP socket, and the real script. It does **not** confirm GHCR's own
media-type acceptance, `Location` semantics or auth quirks under a live write.
The first real run should be a manual `workflow_dispatch` on a scratch
component, with the promotion record's digests compared by hand before any
tag-cut release is allowed to run.

Fleet-scope go-ahead for an actual GHCR write / fleet rollout is deliberately
still outstanding — this PR builds and proves the mechanism only.
