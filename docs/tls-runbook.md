# TLS runbook — Caddy's own internal CA at the edge (fleet-ops-f57.13,
# rewritten to automate rotation — see the PR that introduced this version)

The master device's composition (registrar + postgres + the VS gateway)
is fronted by caddy; TLS is served from **Caddy's own built-in local CA**
(`tls internal`) — the fleet still never trusts a third party for device
identity, but the CA now lives inside Caddy's own PKI storage instead of
on the owner's machine. Caddy mints its root CA, its leaf certs, and
renews the leaves automatically, with zero owner action, for as long as
its data volume persists. This supersedes the earlier owner-run
`scripts/gen-vs-ca.sh` + `certs-init` + manual-paste design: there is no
script to run, no fleet-variable cert pair, and no ~25-day rotation
chore.

**The one custody trade this makes:** the CA private key used to move
from "owner's trusted host only, never in the repo/image/chat" to "on the
registrar device's own persistent volume." The registrar is already its
own single-purpose, single-failure-domain balena appliance
(balena-architecture.md), so this trades a stricter custody boundary for
zero-touch rotation. If that trade is ever reconsidered, the previous
owner-custodied design is recoverable from git history.

## What is where

| Piece | Lives where | Secret? |
|---|---|---|
| CA key + leaf key | `caddy-data` named volume on the registrar device, under `/data/caddy/pki/authorities/local/` — self-generated by Caddy, never written by the owner | Yes — but never leaves the device; nothing external ever reads it |
| CA root cert (`root.crt`) | Same volume; extracted (read-only) by the owner once, then shipped to devices via `VS_CA_CERT_B64` | No (public material) |
| `balena/registrar/Caddyfile` | repo, baked into the caddy image | No |
| `caddy-data` volume | master device composition; **must be a named/persistent volume** — wiping it forces a CA roll (see below) | No |

## Certificate lifetimes

Caddy manages both the CA and leaf lifetimes itself via its automatic
HTTPS machinery (the same renewal logic it uses for real ACME certs, just
pointed at its local CA): it renews a certificate once a fixed fraction
of its lifetime remains (`renewal_window_ratio`, Caddy default 1/3) and
re-checks on a fixed interval (`renew_interval`, Caddy default 10
minutes). No cron job, no window to track, no "run this every ~25 days"
— this entirely replaces the previous 30-day-leaf/180-day-CA manual
window. If you ever want to tune either lifetime, see Caddy's `pki`
and top-level TLS global options (`cert_lifetime`, `renewal_window_ratio`);
the defaults need no owner attention.

## Owner steps (first setup)

1. **Deploy** — tag the release carrying this Caddyfile (e.g.
   `registrar-v1.2.0`), wait for the device to pull it. Caddy starts,
   self-provisions its local CA (root + intermediate) and a leaf for
   `TLS_HOSTNAME`, and begins serving — nothing to generate beforehand.

2. **DNS** — add the Pi-hole record: `vsigma.lan -> <master device LAN
   IP>` (unchanged from before — local DNS only, the hostname never needs
   to be public).

3. **Fleet variable** (balenaCloud dashboard, `registrar` fleet scope):

   | Variable | Value | Notes |
   |---|---|---|
   | `TLS_HOSTNAME` | `vsigma.lan` | the Caddyfile's `{$TLS_HOSTNAME:...}` — this is the ONLY TLS fleet variable now |

4. **Confirm caddy is serving** — from a trusted LAN host, extract the CA
   root cert it just minted (balena CLI or the dashboard's device
   terminal, on the **caddy** service):

   ```bash
   balena ssh <device-uuid> caddy
   cat /data/caddy/pki/authorities/local/root.crt
   # copy the PEM output, or:
   ```

   or, from any machine with the balena CLI and no interactive shell
   needed:

   ```bash
   balena ssh <device-uuid> caddy \
     -c "base64 -w0 /data/caddy/pki/authorities/local/root.crt" \
     > vs-ca-b64.txt
   ```

   Then sanity-check the edge itself:

   ```bash
   balena ssh <device-uuid> caddy -c \
     "cat /data/caddy/pki/authorities/local/root.crt" > vs-ca.crt
   curl -s https://vsigma.lan/healthz --cacert vs-ca.crt
   # {"status":"ok"}
   ```

5. **Provision device CA trust — BEFORE the URL flip** (same hazard the
   original f57.13 review flagged: the registrant aborts on an https URL
   with no CA provisioned, so flipping the URL first takes every device
   down during the window). Set ONE fleet variable on the `devices`
   fleet, using the base64 you extracted in step 4:

   ```
   VS_CA_CERT_B64=<single-line base64 of the extracted root.crt>
   ```

   The registrant image's entrypoint shim decodes it to
   `NODE_EXTRA_CA_CERTS` before the registrant starts. The registrant's
   config layer enforces the contract fail-loud: an https `REGISTRAR_URL`
   with no CA provisioned aborts startup naming the variables (no silent
   public-CA fallback — the f57.8 posture). `http` URLs (compose-internal,
   pre-TLS topologies) boot unchanged.

6. **Flip the devices** — the `devices` fleet's `REGISTRAR_URL` becomes
   `https://vsigma.lan` (port 443 = registrar's front door; no port
   suffix). With device CA trust already provisioned (step 5) a device
   bootstrapping at any moment of the flip resolves a working pair —
   its https URL has a live edge AND a provisioned CA. A device
   bootstrapping BEFORE the release lands still runs its old http URL —
   the release flip is the last moving part, not the middle one.
   Order: CA trust (5) → release verified serving (4) → flip.

**The clock gate is still load-bearing:** a device with a wrong clock
fails the cert validity window before it can bootstrap — time-sync-
before-TLS is exactly the guard the clock gate was built for, unchanged
by this rewrite.

## Rotation

Nothing to do. Caddy renews its own leaf certs automatically, well before
expiry, with no fleet-variable update and no service restart. Devices
keep working through every renewal — their trust is in the CA (which
does not change on a routine leaf renewal), not the leaf.

## CA roll (only if you deliberately want a new root — e.g. suspected key
exposure, or wiping a device for a clean start)

1. Stop the composition, then wipe the `caddy-data` volume — balena
   dashboard: caddy service → ⋯ actions → **Purge data**; self-host:
   `docker volume rm <project>_caddy-data`. (A targeted
   `rm -rf /data/caddy/pki` via a device terminal, then restarting the
   caddy service, works too and is less destructive to any other state
   Caddy might keep on that volume.)
2. Restart the composition. Caddy mints a fresh root CA + leaf
   automatically — no script, no input needed.
3. Re-extract the new root cert (owner steps 4–5 above) and re-push
   `VS_CA_CERT_B64` on the devices fleet.
4. Restart the devices' registrant services. Devices with the cached old
   CA reject the new leaf until re-provisioned — expected; the restart
   re-decodes the new CA from the fleet variable.

## Failure notes

- **caddy fails to start / restart-looping**: check `docker logs
  <container>` (or the balena dashboard's service logs) for a PKI
  provisioning error — almost always a volume permissions issue on
  `caddy-data`, not a certificate problem (there is no fleet-variable
  pair to mistype anymore).
- **Device fails TLS handshake**: wrong clock (cert not-yet-valid /
  expired from the device's view — wait for NTP) or stale
  `VS_CA_CERT_B64` (re-extract after a deliberate CA roll — see above;
  routine leaf renewals never require this).
- **`curl` from the LAN without `--cacert` fails**: correct — that is
  the posture. Trust the CA or stay out.
- The balenaCloud **public URL** (tunnels device port 80) lands on
  caddy's redirect-to-TLS: plain-HTTP console access through the tunnel
  is dead by design. Use https from a trusted host, or enable the
  public-URL toggle only for the https port if you need remote access.
